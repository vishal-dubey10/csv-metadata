### FEAT-003 — Lambda Worker Handler (Day 2)

**Delivered:**
- `worker/handler.py` — SQS event handler:
  1. Parses SQS event (batch size 1)
  2. Calls `claim_job_for_processing()` — atomic conditional UPDATE, returns False if already completed
  3. Downloads raw CSV from `s3://csvforge-files-dev/uploads/{s3_key}` using `s3_client.py`
  4. Delegates to `csv_processor.parse_and_analyse()` — parse, validate, clean, deduplicate
  5. Uploads result to `s3://csvforge-files-dev/processed/{user_id}/{job_id}/cleaned_{filename}`
  6. Calls `complete_job()` — stores row_count, column_count, duplicate/blank row stats
  7. On `InvalidCSVError`: calls `fail_job()`, returns cleanly (SQS deletes message)
  8. On any other exception: re-raises (SQS retries after visibility timeout)
- `worker/csv_processor.py` — CSV processing: UTF-8 validation, header checks, duplicate detection, blank row removal, whitespace trimming
- `worker/exceptions.py` — `InvalidCSVError` (permanent failure, no retry)
- Full unit test suite: 140 tests covering all handler paths, all CSV validation scenarios, idempotency, user_id sourcing

## Architecture — The Factory Analogy

CSVForge maps to a factory:

```
Customer (Browser) → Reception Desk (FastAPI)
                             ↓
                     issues visitor pass (presigned PUT URL)
                             ↓
Customer drops materials at Warehouse Loading Dock (S3 uploads/)
                             ↓
Reception Desk issues Work Order (SQS message with job_id)
                             ↓
Work Order Conveyor Belt (SQS queue)
                             ↓
Temporary Worker (Lambda) picks up order
    - reads raw materials from warehouse (S3 GetObject)
    - processes them (csv_processor.py)
    - stores finished goods in Finished Goods Storage (S3 processed/)
    - updates Factory Ledger (PostgreSQL: status=completed)
    - tears up the work order (SQS DeleteMessage)
                             ↓
Customer checks Factory Ledger (GET /jobs/{job_id})
    - status=completed
Customer picks up finished goods via delivery pass (presigned GET URL)
    - downloads cleaned CSV directly from Finished Goods Storage
```

Key insight: **The Reception Desk (FastAPI) never touches the goods (CSV bytes).**
It handles paperwork (job records), coordinates (presigned URLs), and schedules work (SQS messages).
The actual work happens in the warehouse (Lambda + S3).

## Failure Experiments Summary

### Failure 1 — Lambda Crashes Mid-Processing (Transient)
- **What failed:** Lambda exits with unhandled exception
- **Who detected:** SQS visibility timeout expiry (no DeleteMessage received)
- **Who retried:** SQS re-delivered after 1800s; ESM invoked Lambda again
- **State preserved:** Job in `processing` in PostgreSQL; idempotency guard allows re-claim
- **Where message went:** Retried up to 5 times; then moved to DLQ
- **Duplicate guard:** `claim_job_for_processing()` conditional UPDATE allows re-claim of `processing` jobs

### Failure 2 — Duplicate Delivery (At-Least-Once)
- **What failed:** SQS delivered same message twice (normal SQS Standard behavior)
- **Who detected:** Second Lambda invocation — `claim_job_for_processing()` returned False
- **Who retried:** No retry needed — job already `completed`
- **State preserved:** Job `completed` in PostgreSQL from first invocation
- **Where message went:** Second invocation deleted the duplicate message
- **Duplicate guard:** `WHERE status IN ('queued','processing')` — `completed` jobs are immune

### Failure 3 — Missing S3 Object
- **What failed:** S3 `GetObject` raises `ClientError(NoSuchKey)`
- **Who detected:** Worker (boto3 exception propagated)
- **Who retried:** SQS re-delivered after visibility timeout (ClientError is not InvalidCSVError)
- **State preserved:** Job stuck in `processing`; retries attempt re-claim
- **Where message went:** 5 retries → DLQ (permanent failure for missing file)
- **Duplicate guard:** Retries are safe — S3 PutObject is idempotent on the same key

### Failure 4 — Repeated Failure → DLQ
- **What failed:** Message failed MaxReceiveCount=5 times
- **Who detected:** SQS (ReceiveCount exceeded MaxReceiveCount)
- **Who retried:** SQS moved message to DLQ — no more retries
- **State preserved:** Message body preserved in DLQ for 14 days
- **Where message went:** `csvforge-jobs-dlq-dev`
- **Replay:** `sqs receive-message` from DLQ → `sqs send-message` to main queue → `sqs delete-message` from DLQ

## Distributed Systems Concepts Demonstrated

| Concept | Where in CSVForge |
|---|---|
| Asynchronous processing | API returns "queued"; Lambda processes later |
| Decoupling | FastAPI and Lambda never call each other; SQS is the intermediary |
| At-least-once delivery | SQS Standard queue — duplicates handled by idempotency guard |
| Idempotency | `claim_job_for_processing()` conditional UPDATE |
| Visibility timeout | 1800s on `csvforge-jobs-dev` |
| Dead-letter queue | `csvforge-jobs-dlq-dev` after 5 failures |
| Backpressure | SQS queue depth grows when Lambda can't keep up |
| Failure isolation | Lambda crash doesn't affect FastAPI |
| Retry | SQS automatic re-delivery up to MaxReceiveCount |
| Durability | S3 (11 nines), PostgreSQL (RDS backups), SQS (multi-AZ) |
| Least privilege IAM | Lambda role has exactly 4 permissions; nothing more |
| Control plane vs data plane | IAM/queue setup vs CSV bytes/SQS messages |
